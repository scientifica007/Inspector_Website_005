# منصة التفتيش المهني — Inspector_Website_005

منصة ويب عربية (RTL) مكتوبة بـ Django تساعد مفتش التكوين والتعليم المهنيين على
إدارة الزيارات التفتيشية، وتكوين نطاقها بحرية، وتنفيذها، ثم تصديرها، مع حماية
صريحة للحقيقة التاريخية للزيارات السابقة.

الواجهة عربية بالكامل واتجاهها من اليمين إلى اليسار، والتواريخ تُعرض بصيغة
`dd/mm/yyyy` فقط. التطبيق مُخدَّم من الخادم (server-rendered) ويعمل على الحاسوب
والهاتف.

---

## 1. الفكرة الأساسية: أربعة مفاهيم منفصلة

| المفهوم | المعنى |
| --- | --- |
| **Reference (مرجع)** | مكتبة أو مرجع قابل للاقتباس. توجد عدة مراجع مستقلة وصالحة بالتوازي؛ لا يوجد «مرجع رئيسي واحد» يحل محل ما قبله. |
| **Visit (زيارة)** | حدث تفتيش فعلي مستقل، يحمل **لقطة مجمّدة** من مرجعه. |
| **Guide (دليل)** | اقتراح **اختياري** قابل لإعادة الاستخدام، يطبّقه المفتش صراحة داخل مسودة. |
| **Assignment (تكليف)** | تكليف **رسمي** بمرحلتين (مسودة ثم إصدار)، يستهدف عناصر محددة داخل مسودة زيارة موجودة. |

> **لا يوجد مفهوم `FREE / GUIDED / LOCKED` على مستوى الزيارة.**
> الزيارة نفسها ليست حرّة ولا موجّهة ولا مقيّدة. الاقتراحات والقيود تُطبَّق على
> **عناصر محددة** داخل الزيارة.

الفارق الجوهري بين الدليل والتكليف:

* **الدليل يقترح** — لا يقفل عنصرًا ولا يجعله متطلب إتمام.
* **التكليف يُلزم** — يستطيع فرض `scope_locked` أو `completion_required` أو كليهما،
  وهما مفهومان **مستقلان**.

## 3. الأدوار والصلاحيات

الصلاحيات مفروضة **على الخادم** في طبقة العروض والخدمات، لا بإخفاء الأزرار فقط.
إخفاء عناصر الواجهة تحسين تجربة، وليس آلية أمنية.

### ADMIN

* إدارة المؤسسات.
* إنشاء وتحرير المراجع المشتركة وبنيتها الهرمية.
* إنشاء الأدلة ونشرها.
* مراجعة مقترحات تعميم المراجع الخاصة: قبول أو رفض.
* إنشاء التكليفات وإصدارها وإلغاؤها (قبل إكمال الزيارة).
* إدارة المستخدمين (إنشاء، تعديل، تفعيل/تعطيل).
* قراءة أي زيارة وتصديرها لأغراض التدقيق.

### INSPECTOR

* رؤية المراجع المشتركة والاقتباس منها.
* إنشاء مراجع خاصة به وتعديلها وحذفها وفق قواعد سلامة البيانات.
* اقتراح تعميم مرجع خاص للمراجعة.
* إنشاء الزيارات وتكوين نطاقها بحرية.
* إضافة محتوى محلي داخل الزيارة.
* تطبيق دليل اختياري داخل مسودة متوافقة.
* رؤية التكليفات الرسمية الصادرة إليه.
* تنفيذ الزيارة، استكمالها، تصديرها.
* حذف مسوداته فقط.

### سياسة حذف المسودات

* صاحب الزيارة يستطيع حذف مسودته.
* **لا يُسمح بحذف زيارة مكتملة** — `COMPLETED` حقيقة تاريخية محمية.
* **لا يستطيع المدير حذف مسودة مفتش آخر.** المسودة ملك لصاحبها؛ قرار هندسي
  يحفظ الملكية ويمنع التلاعب الإداري بأعمال جارية. الإدارة تراجع وتقرأ، لكنها
  لا تحذف عمل مفتش لم يُكمل بعد.
* حذف مسودة مفتش آخر يُرفض بـ `403 Forbidden`؛ أما محاولة حذف زيارة مكتملة
  فتُرفض كقاعدة عمل مع رسالة واضحة في الواجهة.

## 4. كيف تُحمى الحقيقة التاريخية

الزيارة التي أُنشئت من مرجع تحصل على **لقطة مجمّدة** مستنسخة داخل الزيارة نفسها.
بعد ذلك:

| الحدث | الأثر على الزيارة |
| --- | --- |
| تعديل المرجع الأصلي | **لا شيء** — اللقطة لا تتغير. |
| حذف المرجع الأصلي | **لا شيء** — الزيارة تبقى كاملة وتحتفظ بعنوان المرجع وإصداره. |
| إضافة عناصر للمرجع لاحقًا | لا تظهر في الزيارات القديمة. |
| تغيير دليل بعد تطبيقه | لا يُعاد كتابة الزيارة. |
| حذف دليل بعد تطبيقه | يبقى أثر التطبيق محفوظًا مع اسم الدليل وإصداره. |
| تعديل مرجع خاص بعد إرساله للمراجعة | لا يغيّر المادة التي يراجعها المدير (لقطة إرسال ثابتة). |
| إلغاء تكليف | يُزال الالتزام الناتج عنه فقط، وتبقى أي قيود أساسية أو من تكليف آخر. |
| إكمال الزيارة | تصبح غير قابلة للتغيير تمامًا: لا نتائج، لا نطاق، لا تكليفات، لا حذف. |

### المرجع الحي مقابل اللقطة المجمّدة

* **المرجع الحي:** قابل للتحرير، ويتطور عبر إصدارات.
* **اللقطة المجمّدة:** نسخة ثابتة داخل الزيارة، تحمل المعرّفات الثابتة والعناوين
  وقت الإنشاء.

عند مطابقة عنصر (من دليل أو تكليف أو تصدير) تُستخدم **المعرّفات الثابتة**
(`code`)، وهي فريدة داخل المرجع ولا يُعاد استخدامها.

## 5. سير العمل النموذجي

1. **المدير** ينشئ مرجعًا مشتركًا ويبني شجرته: فروع، أوصاف/مواصفات، بنود تفتيش.
2. **المفتش** ينشئ زيارة: يختار المؤسسة والتاريخ والمرجع.
3. يحصل المفتش على **لقطة مجمّدة** كاملة، لكن **نطاق التفتيش يبدأ فارغًا**.
4. يختار المفتش ما يريد تفتيشه: فرعًا كاملًا، وصفًا، بندًا، أو محتوى محليًا.
   اختيار بند عميق يُظهر **الأسلاف للسياق** فقط، لا كعناصر مختارة.
5. **المدير** يمكنه إصدار تكليف رسمي مرتبط بمسودة الزيارة، يفرض قيد نطاق أو
   متطلب إتمام على عناصر محددة.
6. **المفتش** ينفّذ الزيارة: يسجّل نتيجة كل بند وملاحظاته.
7. يتحقق النظام من المتطلبات الإلزامية، ثم يُكمل المفتش الزيارة.
8. **تصدير** الزيارة بصيغة JSON واضحة ومُصدَّرة بإصدار.

### المصادر (Origin)

كل عنصر دخل النطاق يُسجَّل مصدره، ولا يُمحى المصدر الأصلي أبدًا:

| المصدر | المعنى |
| --- | --- |
| `LEGACY` | عنصر كان مختارًا أصلًا بحكم قديم. |
| `MANUAL` | اختاره المفتش بنفسه. |
| `GUIDE` | دخل بسبب تطبيق دليل. |
| `ASSIGNMENT` | دخل بسبب تكليف رسمي. |
| `LOCAL` | محتوى محلي أنشأه المفتش داخل الزيارة. |

مثال: عنصر دخل بسبب `MANUAL` ثم طُبِّق عليه دليل أو تكليف — **يبقى مصدره
`MANUAL`**. التكليف يضيف التزامًا، ولا يغيّر المصدر.

### النطاق الانتقائي: مختار مقابل سياق

الزيارة الجديدة **لا تبدأ بكل عناصر المرجع**. النطاق يبدأ فارغًا، ويضيف المفتش
ما يريد. عند اختيار بند عميق تُعرض الأسلاف للسياق، لكن:

* **SELECTED** — عنصر مختار فعلًا، يدخل في حساب الإنجاز.
* **CONTEXT** — عنصر ظاهر للسياق فقط، **لا يدخل في حساب الإنجاز**.

حساب التقدم يعتمد فقط على العناصر النشطة المختارة والقابلة للإنجاز، ولا يحتسب
العناصر المستبعدة ولا عقد السياق الهيكلية. يُعرض بصيغة مثل `3 / 5` و `60%`.

### الاستبعاد اللطيف (Soft Exclusion)

الاستبعاد **ليس حذفًا**. العنصر المستبعد يحتفظ بنتيجته وملاحظاته، ويستطيع المفتش
استرجاعه بنفس بياناته السابقة. تُستخدم `ACTIVE` / `EXCLUDED` مع الحفاظ على كل
البيانات المسجلة.

### نتائج البنود

| النتيجة | الرمز |
| --- | --- |
| مطابق | `MATCH` |
| غير مطابق | `NOT_MATCH` |
| غير منطبق | `NOT_APPLICABLE` |

**«غير منطبق» ≠ «غير مطابق».** الأول يعني أن البند لا ينطبق على هذه المؤسسة أو
هذا المسار، والثاني يعني أنه ينطبق ووُجد مخالفًا. رمزان مختلفان تمامًا، ولا
يُخلط بينهما في التخزين ولا في التصدير ولا في حساب الإنجاز.

مع كل بند يمكن تسجيل **ملاحظة/مشاهدة**. والوصف/المواصفة يمكن أن يحمل قيمة من
نوع نص أو عدد أو تاريخ أو نعم/لا.

### المحتوى المحلي

داخل المسودة يستطيع المفتش إضافة فرع محلي أو وصف محلي أو بند محلي. هذا المحتوى
يبقى **داخل الزيارة**، ولا يُرسل تلقائيًا إلى الإدارة:

```
Local Visit Authoring  ≠  Governance Submission
```

### الاقتراح ليس أمرًا

تطبيق الدليل **متكرر بأمان (idempotent)**: تطبيق الدليل نفسه مرتين لا يضيف شيئًا
في المرة الثانية، ولا يكرّر العناصر الموجودة. وعند التطبيق:

* تُضاف العناصر غير الموجودة فقط.
* يُحفظ المصدر الأصلي لكل عنصر موجود.
* العناصر التي دخلت بسبب الدليل فقط يكون مصدرها `GUIDE`.
* الدليل **لا يقفل** عنصرًا ولا يجعله `completion_required`.

إذا احتوى الدليل على عنصر **غير موجود في اللقطة المجمّدة** (تباعد زمني):

* **لا** يُسحب من المرجع الحي.
* يُطبَّق المتوافق فقط، ويُتخطّى غير المتوافق بصورة واضحة ومُبلَّغة.

### التكليف: مرحلتان

| المرحلة | الحالة | الظهور |
| --- | --- | --- |
| مسودة إدارية | `DRAFT` | لا تظهر للمفتش؛ قابلة للتحرير. |
| صادر | `ISSUED` | يظهر للمفتش؛ يصبح سجلًا رسميًا. |

كل تكليف يحتوي بنودًا، وكل بند يستهدف عنصرًا داخل اللقطة المجمّدة (فرع، وصف، أو
بند) ويمكنه فرض `scope_locked` أو `completion_required` أو كليهما — وهما
**مستقلان**:

* `scope_locked` — لا يستطيع المفتش إخراج العنصر من النطاق. وبالنسبة إلى فرع،
  يُطبَّق القيد على الفرع وشجرته الفرعية معًا حتى لا يمكن الالتفاف حوله.
* `completion_required` — لا يمكن إكمال الزيارة حتى يُستوفى العنصر. ويُطبَّق على
  العناصر القابلة للإنجاز، لا على عقدة هيكلية فارغة.

الإصدار **ذرّي (Atomic)**: تُفحص كل البنود أولًا. إذا كان هدف واحد غير صالح
**لا يُصدر أي جزء**. إما الكل أو لا شيء.

### القيود الأساسية مقابل السارية

* **Baseline Constraints** — تأتي من إعدادات المرجع نفسه (مثل بند إلزامي)،
  وتُلتقط في اللقطة. لا تمحى أبدًا بإلغاء تكليف.
* **Effective Constraints** — المحصلة النهائية الآن = الأساسية + التكليفات الصادرة.

هذا الفصل هو ما يجعل **إلغاء تكليف** لا يمحو قيدًا كان موجودًا أصلًا، ولا يمسّ
التزامًا فرضه تكليف آخر. عند تداخل تكليفين على العنصر نفسه:

* تكليف `A` يفرض `scope_locked`، وتكليف `B` يفرض `completion_required`.
* إلغاء `A` يزيل قفل `A` فقط، ويبقى متطلب `B` ساريًا.

### الإلغاء (Revocation)

يستطيع المدير إلغاء تكليف **صادر** فقط، وبشرط أن تكون الزيارة ما تزال `DRAFT`.
يجب طلب **سبب**، ويُسجَّل: من ألغى، ومتى، والسبب.

الإلغاء **لا** يحذف بيانات الزيارة، ولا يحذف اللقطة، ولا يستبعد العناصر؛ يزيل
فقط الالتزامات التي لم يعد لها مبرر من تكليف آخر أو من القيود الأساسية.

بعد `COMPLETED`: لا إصدار، ولا إلغاء، ولا إعادة تفسير.

## 6. مخرجات التصدير (Export)

`GET /visits/<id>/export/` يعيد JSON مُصدَّرًا بإصدار:

```json
{
  "schema": "inspector.visit.export",
  "version": 2,
  "visit": { "...": "الهوية، المؤسسة، المفتش، التاريخ، الحالة" },
  "scope": { "nodes": [], "active_count": 0, "context_count": 0 },
  "constraints": { "baseline": {}, "effective": {} },
  "assignments": [],
  "guide_applications": [],
  "assignment_audit": {},
  "progress": { "done": 0, "total": 0, "percent": 0 }
}
```

يمثّل التصدير على الأقل: هوية الزيارة، المؤسسة، المفتش، التاريخ، الحالة، المرجع
ومصدره التاريخي وإصداره، نطاق الزيارة، `Selected` مقابل `Context`، `Active`
مقابل `Excluded`، `origin`، الأقفال، متطلبات الإتمام، القيم، النتائج، الملاحظات،
سجل التكليفات الكامل، والتكليفات الملغاة مع أسبابها.

الخصائص المهمة:

* **حتمي (Deterministic):** تصدير الزيارة نفسها مرتين يعطي نفس البايتات
  (`sort_keys=True`). لا تُضاف طوابع زمنية متغيرة تفسد المقارنة، ولا وقت حائط
  لحظي — فقط الحقائق التاريخية المخزنة.
* يُضاف `?download=1` لتنزيل الملف باسم `visit-<id>-export-v<version>.json`.
* يرفض التصدير أي مفتش آخر (403)؛ ويمكن للمدير قراءة أي زيارة.

| `accounts` | المستخدم المخصص، الأدوار، المصادقة، صلاحيات الخادم، إدارة المستخدمين. |
| `institutions` | المؤسسات الخاضعة للزيارات. |
| `catalog` | المراجع، العقد الهرمية، المراجع الخاصة، طلبات التعميم. |
| `visits` | الزيارات، اللقطات المجمّدة، النطاق الانتقائي، التنفيذ، الإتمام، التصدير. |
| `governance` | الأدلة، التكليفات، فصل القيود الأساسية عن السارية. |
| `core` | أدوات مشتركة، فلاتر الواجهة، أمر بيانات العرض، مصانع الاختبار. |

### المبادئ المطبَّقة

* **فصل المسؤوليات:** منطق النظام المركّب في `services.py` لكل تطبيق، وليس في
  العروض. العروض تتولى المصادقة والصلاحيات والتوجيه والعرض.
* **التحقق من جهة الخادم:** كل مدخل يمر عبر Django Forms أو تحقق خدمة صريح.
* **CSRF** مفعّل على كل النماذج، مع `transaction.atomic` على العمليات المركّبة
  (إنشاء الزيارة، الإصدار، الإلغاء، الإكمال).
* **قيود قاعدة البيانات** عند الحاجة، مثل منع تكرار بند في التكليف نفسه.
* **لا اعتماد أمني على JavaScript.** JS المستخدم خفيف ومحسّن للتجربة فقط.
* **قابلية الانتقال إلى PostgreSQL:** الاتصال كله من متغيرات البيئة؛ لا شيء في
  الكود يعتمد على SQLite، والترحيلات قياسية.

### العرض والتواريخ

* `dir="rtl"` و `lang="ar"` على كل الصفحات، مع `viewport` مناسب للهاتف.
* التواريخ تُعرض عبر فلتر `ardate` بصيغة `dd/mm/yyyy` — **لا `mm/dd/yyyy` أبدًا**.
* مدخلات التاريخ تقبل `dd/mm/yyyy` و `%Y-%m-%d`، ومنتقي التاريخ في المتصفح يمنع
  الالتباس.
* جداول الموبايل قابلة للتمرير أفقيًا، والأزرار بحجم مناسب للمس، والقوائم قابلة
  للاستعمال على شاشة ضيقة، و RTL سليم.

## 8. الاختبارات

```bash
python manage.py test                              # المجموعة الكاملة
python manage.py test visits                       # تطبيق واحد
python manage.py test visits.tests.test_workflow   # مسار كامل عبر العروض
```

المجموعة تغطي، من بين ما تغطيه:

* المصادقة والصلاحيات، بما فيها منع مفتش من زيارة مفتش آخر.
* إنشاء المراجع وتحريرها وحذفها، وخصوصية المراجع الخاصة.
* لقطة إرسال المرجع الخاص، والقبول/الرفض، واستقلال المرجع المشترك الناتج.
* اللقطة المجمّدة واستقلال الزيارة عن حذف المصدر أو تغييره.
* النطاق الانتقائي، والبند العميق مع أسلاف السياق.
* الاستبعاد والاسترجاع مع سلامة النتائج والملاحظات.
* المحتوى المحلي، والأدلة، وتكرار التطبيق بأمان، والتباعد الزمني.
* التكليفات، والإصدار الذرّي، والتداخل، والقيود الأساسية، والإلغاء.
* منع الإكمال، وثبات الزيارة المكتملة، وحذف المسودات.
* التصدير وحتميته، وواجهة RTL وصيغة التاريخ والاستعمال على الهاتف.
* أمر بيانات العرض: الفعالية، وعدم الإتلاف، وعدم إعادة تعيين كلمات المرور.

## 9. النشر

للنشر في بيئة حقيقية:

1. اضبط `DJANGO_SECRET_KEY` بمفتاح قوي عشوائي.
2. اجعل `DJANGO_DEBUG=0`.
3. اضبط `DJANGO_ALLOWED_HOSTS` بنطاقك الفعلي.
4. اضبط `DJANGO_CSRF_TRUSTED_ORIGINS` إذا عملت خلف وكيل عكسي.
5. انتقل إلى PostgreSQL عبر متغيرات `DB_*`.
6. شغّل `python manage.py collectstatic` و `python manage.py migrate`.
7. شغّل التطبيق عبر خادم WSGI حقيقي (مثل Gunicorn) خلف وكيل يتولى HTTPS.
